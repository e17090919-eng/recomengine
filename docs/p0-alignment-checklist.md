# P0 客户对齐清单（首个客户：CDF）

每一项都标了负责人和对应的交付物。勾选完成后就可以进入 P1。

## A. 规模与目标
- [ ] 目标 APP / 渠道：cdf 会员购 / 中免会员 / 海南小程序 / 新西兰门店的线上渠道
- [ ] 每个市场的 DAU、商品 SPU 数、峰值 QPS（含大促和黄金周）→ 用于更新方案 §0.2 的容量估算
- [ ] 首批上线场景和成功指标（建议：首页猜你喜欢的 CTR 和人均 GMV，护栏指标是延迟和负反馈率）
- [ ] 当前推荐逻辑是什么（作为 A/B 实验的对照组）

## B. 数据（交付物：字段映射文件 `configs/mappings/cdf_<market>.toml`）
- [ ] 埋点平台和导出方式（神策、GrowingIO、自建数仓……），拿一份样例数据（1 天的量）
- [ ] 逐项对照 [`tracking-spec.md`](tracking-spec.md)：有没有**曝光事件**？有没有 request_id？SPM 是否能拼出来？
- [ ] 会员表：会员等级的编码、国籍、语言、已用额度字段
- [ ] 商品表：SPU 和 SKU 的关系、类目体系、品牌、多语言标题、参考价
- [ ] 各门店/市场的价格、库存、提货方式
- [ ] 历史数据：时间跨度、数据量、时区、交付方式
- [ ] 用样例数据跑通 `recsys backfill`，回灌报告和数据质量报告要和客户一起确认

## C. 业务规则（交付物：`configs/engine.toml` 的 markets 段）
- [ ] 每个市场的免税额度（海南离岛年度额度）及额度查询接口，实时性如何
- [ ] 限购规则（类目、件数、容量、周期）
- [ ] 提货和配送渠道，以及不同用户身份能用哪些渠道（离岛旅客、岛内居民、跨境、有税）
- [ ] 品牌方的陈列要求和新品保量需求
- [ ] 不能推荐的商品（违禁品、处方药、仅限门店销售的商品……）

## D. 系统对接
- [ ] 推荐接口由谁调用：APP 后端（Java）还是客户端，网络在哪里（专线、公网、同一个 VPC）
- [ ] 实时数据怎么同步：行为数据走 SDK 转发还是服务端写入；商品和库存走 CDC 还是定时推送
- [ ] 鉴权方式（Tenant 签名）和 IP 白名单

## E. 部署与合规
- [ ] 部署方式：客户私有云 / 专有云 / 我方托管；有没有 GPU
- [ ] **中国区数据留在境内**；新西兰区单独部署（Privacy Act 2020）
- [ ] 个人信息处理协议；是否需要"关闭个性化推荐"的开关（中国法规要求提供）
- [ ] 监控、告警的对接方式和值班安排

## P0 完成标准
1. 拿到真实样例数据并完成回灌，数据质量门禁通过（或已知的告警都有处理方案）
2. 基于真实数据输出离线基线报告（Hot / Swing / GBDT）
3. 本地和测试环境的基础设施可用
4. 方案 §0.2 的容量估算按真实数据更新
